## D-001. Проверки драйвера зависят от того, что оставил предыдущий блок

- **Заведён:** 2026-08-22
- **Где:** `.claude/skills/run-archgrid/driver.mjs`, режим `interactions`
- **Что сломано:** не продукт, а проверки. Прогон падает на шаге «and opens the one you click».
- **Серьёзность:** блокирует зелёный прогон, то есть блокирует приёмку любой следующей работы.

### Симптом

```
[archgrid] OK   the panel names every view the element is on — On 2 views: driver 15484, driver 15484 b
[archgrid] DRIVER FAILED: locator.click: Timeout 30000ms exceeded
   waiting for element to be visible, enabled and stable
   element is not enabled
```

### Непосредственная причина

Проверка кликает по ссылке представления в панели свойств:

```js
await page.locator('.ag-props-group li .ag-link', { hasText: secondView }).first().click()
```

Панель показывает представления, на которых есть элемент, и **ссылка на уже открытое представление
отключена** (`disabled={view.key === currentView}`) — идти некуда. Проверка выбирает ссылку по имени
и потому обязана знать, какое представление открыто. А оно менялось дважды, пока я двигал блоки:
сначала блок выполнялся на втором представлении, потом на первом, потом снова на втором.

### Настоящая причина

`interactions` — один длинный скрипт с состоянием поверх общей dev-базы, и блоки неявно зависят от
того, что оставили предыдущие: какое представление открыто, какие боксы лежат друг на друге, какие
элементы уже созданы. Пока бокс был равен элементу, это сходило с рук. С размещениями (ADR-0014,
один элемент может быть нарисован дважды) связанность начала стрелять: за один вечер три падения
подряд, **ни одно не про продукт**:

1. блок выполнялся на втором представлении, а перезагрузка открывала первое;
2. `keyOf('Ledger')` находил «Ledger (copy)» — другой элемент, на одном представлении;
3. клик по ссылке уже открытого представления (этот дефект).

### Как чинить

1. **Ссылка:** кликать ту, которая доступна, а не ту, чьё имя угадали:
   `page.locator('.ag-props-group li .ag-link:not([disabled])').first()`, и проверять, что имя в
   панели инструментов стало равно тексту этой ссылки.
2. **Блоки:** каждый блок сам создаёт себе условия — своё представление и свои элементы, как уже
   сделано для «the same element, drawn twice». Дешевле, чем чинить связанность по одной.
3. **Дальше:** развести `interactions` на несколько независимых прогонов (каждый со своим
   представлением) — тогда падение одного не уносит остальные и порядок перестаёт значить.

## Состояние работы по ADR-0014 (размещения) на момент остановки

Чтобы не выяснять заново, что проверено, а что нет.

**Сделано и проверено:**

- сервер: миграция `V14` (у бокса собственная идентичность, вложенность между боксами, у линии —
  концы-размещения), репозиторий, DTO, контроллер; полная сборка сервера с тестами зелёная;
- клиент: вся адресация переведена с элементов на размещения; **84/84 `interactions` и 18/18
  `smoke` проходили** сразу после рефакторинга, то есть поведение не изменилось;
- «Draw again» в контекстном меню: второй бокс того же элемента, переживает `Save` и перезагрузку,
  удаление одного из двух оставляет элемент на представлении. Эти три проверки проходили.

**Сделано и НЕ проверено:**

- перетаскивание конца линии на другой бокс того же элемента (`linkTools.SourceArrowhead` /
  `TargetArrowhead`, `validateConnection`, `link:connect` → `onLinkEnds`). Проверки на это нет.
  Правило, которое должно соблюдаться: конец можно перенести **только** на бокс того же элемента —
  диаграмма выбирает, где нарисована линия, но не то, что она утверждает.

**Не написано:**

- ADR-0014 (сам документ), обновление [07-database-schema.md](07-database-schema.md) под `V14`,
  и запись решения в [ADR-0012](adr/0012-archimate-exchange-format.md) §1, которое этим отменяется.
