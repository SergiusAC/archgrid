## 1. Neo4j — отклонён

Три независимых возражения, каждого достаточно.

**1.1. Лицензия блокирует бизнес-модель.**
Neo4j Community — GPLv3, Enterprise — коммерческая лицензия с оплатой за инстанс. При on-prem-поставке у тебя два пути: либо заказчик покупает Neo4j Enterprise (дополнительная строка в бюджете сделки, которую тебе придётся защищать вместо разговора о продукте), либо ты тащишь GPLv3 в свой дистрибутив со всеми последствиями. Это не техническое ограничение, а препятствие в продаже. Проверь актуальные условия лицензирования перед любым решением в эту сторону — но проверять надо *до* того, как код завяжется на Cypher.

**1.2. Масштаб не тот.**
Архитектурный ландшафт крупной компании — порядка 2 000–20 000 элементов и 10 000–100 000 связей. Это единицы-десятки мегабайт. Весь граф помещается в heap приложения целиком. Neo4j решает задачу обхода графов, не помещающихся в память, — задачу, которой у тебя нет и не будет.

**1.3. Операционная стоимость умножается на количество внедрений.**
On-prem означает, что бэкапить, мониторить и обновлять систему будет DBA заказчика. Postgres он умеет. Neo4j — почти наверняка нет. Каждая дополнительная stateful-система удлиняет внедрение и повышает вероятность отказа от пилота.

И решающее: **Postgres тебе нужен в любом случае** — пользователи, тенанты, права, версии модели, вложения, аудит. Связка «Neo4j для графа + Postgres для остального» даёт два источника правды и необходимость согласовывать транзакции между ними вручную. Для одного разработчика это яд.

### Что вместо

- **PostgreSQL 16+ как единственное хранилище.** JSONB для гибких атрибутов элементов, `pgvector` для семантического поиска, полноценные транзакции над всей моделью.
- **Обход графа двухуровневый:**
  - рекурсивные CTE для 90 % запросов (зависимости, дерево вложенности, «кто использует»);
  - **in-memory граф-индекс** (JGraphT или собственная adjacency-структура) для тяжёлого: impact analysis, derived relationships ArchiMate, поиск циклов. Индекс строится на версию модели и кэшируется. Обход 20 000 узлов в памяти — микросекунды.
- **Порт `GraphRepository`** в домене. Если через два года конкретный класс запросов упрётся в производительность — меняется адаптер, домен не трогается.
- Apache AGE (openCypher внутри Postgres) держим как запасной вариант, но **не начинаем с него**: он сырее, чем выглядит, а Cypher тебе не нужен.

## 2. OpenSearch — отклонён для v1

Отдельный JVM-кластер ради поиска по 20 000 объектов — это удвоение операционной сложности on-prem-поставки без выигрыша.

- Полнотекст: `tsvector` + `pg_trgm` (опечатки, подстроки).
- Семантика: `pgvector` с HNSW-индексом.
- Фасеты и фильтры: обычный SQL по JSONB с GIN-индексом.

Порог, за которым OpenSearch оправдан: > ~1 млн векторов либо явное требование заказчика по поиску логов. Продукт такого класса туда не приходит.

## 3. Двойной рантайм Java + Python

Оправдан, но только с жёстко проведённой границей. Правила, которые нельзя нарушать:

1. **Python-сервис не имеет доступа к базе данных. Никогда.** Ни read-only, ни «только для эмбеддингов».
2. **Он полностью stateless.** Контракт: на вход JSON (фрагмент модели + релевантная часть метамодели + запрос пользователя), на выход JSON (*предлагаемые команды изменения модели*). Применяет команды Java — после валидации по метамодели и проверки прав.
3. **Продукт обязан работать при выключенном AI-сервисе.** Это не запасной вариант, это требование: в on-prem-контурах AI регулярно отключают политикой безопасности, а в air-gapped — по определению.
4. **В MVP его не существует.** Первая строка Python-кода пишется в фазе 7.

Следствие для LLM-абстракции: провайдер конфигурируется заказчиком (Claude API, Azure OpenAI, локальный vLLM/Ollama через OpenAI-совместимый endpoint). Твой код знает только про «модель, принимающая промпт и возвращающая структурированный JSON по схеме». Промпты и схемы ответов — твой актив, привязка к вендору — нет.

## 4. Yjs / CRDT — отклонён в текущем виде

Два возражения, второе важнее.

**Техническое.** Yjs — JS-библиотека. При бэкенде на Spring Boot ты либо поднимаешь Node-сайдкар `y-websocket` (третий рантайм в on-prem-поставке), либо берёшь незрелые JVM-биндинги `y-crdt`. Для соло-разработчика это отдельный проект, а не фича.

**Архитектурное.** CRDT — неправильный инструмент для семантической модели. Смысл CRDT: «конфликтов не бывает, любые правки сливаются». Смысл типизированной архитектурной модели: «недопустимые состояния невозможны». Два корректных CRDT-мержа легко дают граф, нарушающий метамодель, и никто этого не заметит, потому что валидировать некому — сервер в CRDT-схеме всего лишь релей.

**Правильное разделение** — и оно точно совпадает с твоей же идеей «semantic model отдельно от visual layout»:

| Слой | Природа конфликтов | Механизм |
|---|---|---|
| Visual layout (координаты, waypoints, стили) | Безобидны | CRDT уместен |
| Semantic model (элементы, связи, типы) | Ломают корректность | Команды через сервер: транзакция → валидация → версия |

Модель ведёт себя как Git, а не как Google Docs. Это и продуктово правильнее: архитектурное изменение — это решение, которое должно проходить review, а не результат случайного мержа.

**Что в MVP:** оптимистичная блокировка по версии представления + presence (курсоры и выделение соавторов) по WebSocket. Presence даёт ~80 % ощущения совместной работы за ~5 % стоимости. Настоящее co-editing — фаза 9.

## 5. React Flow — принят

Выбор верный, лицензия MIT. Три оговорки:

- **Производительность.** React Flow рендерит узлы как DOM и заметно деградирует после ~1 000–2 000 узлов на канвасе. Лечится дисциплиной: *представление — всегда отфильтрованная проекция модели, а не «весь граф»*. Это ограничение продуктово полезно: диаграмма на 3 000 прямоугольников бесполезна для человека.
- **Авто-layout.** Нужен `elkjs` — его layered- и ортогональные алгоритмы дают результат, приемлемый для C4 и ArchiMate. `dagre` для этих нотаций слабее.
- **Не клади семантику в `node.data`.** `node.data` = `{ elementId, viewOverrides }`, не более. Модель живёт в отдельном сторе и синхронизируется с сервером независимо от канваса. Нарушение этого правила — самая частая причина, по которой такие редакторы невозможно потом расширить.

## 6. ArchiMate 3.2 целиком — принятое, но самое рискованное решение

Ты подтвердил полную совместимость с самого начала. Для корпоративных архитекторов (TOGAF-контекст) это правильно и даёт бесплатно формат обмена — ArchiMate Open Exchange File Format, то есть импорт из Archi, BiZZdesign, Sparx.

Цена: ~60 типов элементов, ~11 типов связей и матрица разрешённых связей размером ~60×60, плюс правила деривации связей.

**Способ сделать это выполнимым в одиночку — метамодель это данные, а не код:**

- Матрица разрешённых связей, порядок «силы» структурных связей для деривации и определения viewpoint'ов **транскрибируются из спецификации в машиночитаемый файл** (YAML/JSON) и загружаются при старте. Пишется генератор и валидатор согласованности, а не 3 600 условных операторов.
- **Матрицу нельзя писать по памяти — только из официальных таблиц ArchiMate 3.2 (Приложение B).** Ошибка в матрице означает, что продукт врёт архитектору о корректности его модели, а это единственное, чего целевой пользователь не простит. Заложи в фазу 1 отдельную задачу на сверку и авто-тесты по контрольным примерам из спецификации.
- **UI показывает не 60 типов, а палитру текущего viewpoint'а** (10–15 элементов). Полнота модели ≠ полнота палитры. Это же снимает главное возражение против ArchiMate — «слишком сложно».

**Юридическое.** Метамодель и Open Exchange Format открыты. «ArchiMate» — торговая марка The Open Group; формулировки вроде «ArchiMate-certified» без прохождения сертификации использовать нельзя. Безопасная формулировка — «ArchiMate 3.2-compatible metamodel». Перед маркетинговыми материалами это стоит проверить у юриста: я обозначаю риск, а не даю правовое заключение.

## 7. Что в идее недооценено

Три вещи, которые в `idea_summary.md` упомянуты вскользь, но определяют, получится продукт или нет.

**7.1. Элемент существует независимо от диаграмм.**
Это главное отличие от draw.io и место, где такие продукты чаще всего ломаются в UX. Требуется явное различение двух операций: «убрать с этого представления» и «удалить из модели». Вторая должна показывать, где ещё элемент используется, и требовать подтверждения. Если этого нет, пользователь через месяц перестаёт доверять модели.

**7.2. Версионирование нужно заложить в схему БД в день первый.**
Диффы моделей, привязка ADR к изменению, «архитектура на дату X», review изменений — это и есть «Git» из твоей формулы. Дописать версионирование к готовой схеме без версий практически невозможно: придётся переписать каждый запрос. При этом **сама фича может появиться в фазе 5** — важно, чтобы `commit_id` уже был в таблицах с самого начала.

**7.3. Reconciliation — самая тяжёлая инженерная задача продукта.**
Импорт из K8s/Terraform/OpenAPI создаёт факты, которые нужно слить с моделью, написанной руками. Один и тот же сервис приходит из трёх источников под тремя именами. Нужна модель происхождения данных (у каждого факта — источник, время, уверенность), правила сопоставления, и UI разрешения расхождений. Это фаза 6, и она объёмнее, чем кажется. Не начинай её, пока фазы 1–5 не устоялись.

## 8. Стек к реализации

| Слой | Выбор | Почему |
|---|---|---|
| Frontend | React 19 + TypeScript 6 + Vite 8 | — |
| Канвас | React Flow (xyflow), elkjs для auto-layout | MIT, достаточная зрелость |
| Состояние | Zustand (редактор) + TanStack Query (сервер) + immer (undo/redo) | Разделение клиентского и серверного состояния обязательно |
| Backend | Java 21 + **Spring Boot 4.1**, модульный монолит | Виртуальные потоки, зрелость, ожидания enterprise |
| Домен | Чистый Java без Spring-зависимостей в ядре | Метамодель и валидация тестируются без контекста |
| БД | PostgreSQL 16+ (JSONB, pgvector, tsvector, pg_trgm) | Единственный stateful-компонент |
| Миграции | Flyway | Предсказуемее Liquibase для on-prem-апгрейдов |
| API | REST + OpenAPI 3.1; WebSocket только для presence | GraphQL добавляет сложность, которую соло не окупит |
| Аутентификация | Spring Security, OIDC + SAML 2.0 к IdP заказчика | Своего логина не писать |
| AI (фаза 7) | Python 3.12 + FastAPI, stateless sidecar | Абстракция провайдера LLM |
| Поставка | Docker Compose (пилот) + Helm chart (прод), offline image bundle | Air-gap с первого дня |
| Наблюдаемость | Micrometer + OpenTelemetry, structured logs | Заказчик подключит к своему стеку |

**Компоненты, сознательно НЕ включённые в v1:** Neo4j, OpenSearch, Kafka, Redis, отдельный Node-рантайм, микросервисная декомпозиция, Kubernetes-операторы. Каждый из них должен будет доказать необходимость отдельно — правило простое: любой новый stateful-компонент оплачивается временем каждого внедрения.
