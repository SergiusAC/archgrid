# ADR-0008. Workspace — это репозиторий: один связный граф

- **Статус:** accepted
- **Дата:** 2026-08-17
- **Заменяет:** неявное допущение фаз 1–3, что workspace содержит много независимых моделей

## Контекст

Схема фазы 2 позволяла нескольким моделям существовать внутри одного workspace, и каждая владела своими элементами (`element.model_id`). Обнаружилось при просмотре UI: элемент, заведённый в одной модели, невозможно переиспользовать в другой — «Kafka» в модели платежей и «Kafka» в модели уведомлений оказывались разными объектами с одинаковым именем.

## Решение

**Workspace — это архитектурный репозиторий, и он содержит ровно один связный граф.**

```
Workspace  = репозиторий
  ├── Elements + Relationships   инвентарь: системы, сервисы, Kafka, Redis
  ├── Profiles
  ├── Commits                    история графа
  └── Views (фаза 4)             много; каждое показывает срез
```

Несколько несвязанных ландшафтов — это несколько workspace. Строка `model` сохраняется как носитель графа и указателя `head_commit_id`, но она одна на workspace и из API исчезает.

## Обоснование

Отсутствие переиспользования было симптомом, а не болезнью. Настоящий вред в другом: **вопросы к графу отвечали бы неправильно и молча.**

«Где используется Kafka», impact analysis и drift report из фазы 6 — всё это обходы графа. Обход, ограниченный одной моделью из трёх, вернёт ответ, который выглядит полным и таковым не является. Архитектор примет решение по неполной картине, и ничто в интерфейсе на это не укажет.

Это прямо противоречило собственному принципу продукта, записанному в `docs/02-architecture.md`: «архитектурный граф — source of truth». Source of truth не бывает в трёх экземплярах.

Дополнительно: то, что пользователь создавал как «модель», по смыслу является **представлением** — «контекст платежей», «развёртывание уведомлений». Эта роль занята фазой 4, и после исправления «много именованных штук» встают на своё место, а слово «модель» перестаёт значить две разные вещи одновременно.

## Соответствие практике

| Инструмент | Структура |
|---|---|
| Спецификация ArchiMate | «Модель» — вся совокупность концептов; диаграммы — виды на неё |
| Structurizr | Workspace → одна модель → много views |
| Archi | Файл модели содержит все элементы и все views |

## Что делать со сценариями as-is / to-be

Не отдельными графами. В ArchiMate для этого есть `Plateau` из слоя Implementation & Migration — состояние ландшафта в момент времени, внутри одного графа. Отдельные графы разорвали бы связи между «как есть» и «как будет», то есть ровно ту информацию, ради которой сценарии и строят.

## Последствия

- Миграция `V4` создаёт граф каждому workspace и вводит `unique (workspace_id)` на `model`. При нескольких моделях в одном workspace она **падает с объяснением**, а не сливает их: слияние требует решений о конфликтующих ключах, двух историях коммитов и двух наборах профилей, и ни одно из них не должно приниматься молча.
- Из API исчезает сегмент `/models/{modelKey}`: `/api/workspaces/{ws}/elements`, `/commands`, `/commits`, `/profiles`.
- Граф создаётся лениво при первом обращении к workspace, поэтому чтение никогда не встречает его отсутствия.
- В UI исчезает выбор и создание модели; вкладка, показывавшая элементы, называется «Repository», а не «Model».
- Множественные графы остаются возможными на уровне схемы (ограничение снимается одной строкой), если однажды появится обоснованный сценарий.
