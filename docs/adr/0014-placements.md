# ADR-0014. Бокс на представлении — размещение, а не элемент

- **Статус:** accepted; схема и редактор — сделано (миграция V14); полнота для линий — план V15 ниже
- **Дата:** 2026-08-22
- **Отменяет:** [ADR-0012](0012-archimate-exchange-format.md) §1 («один узел на элемент — принимаем»)
- **Связано с:** [ADR-0003](0003-model-view-layout-separation.md), [ADR-0009](0009-views-and-folders.md),
  [ADR-0011](0011-nesting-is-presentation.md)

## Контекст

До V14 бокс на канвасе *был* элементом: `view_layout_node` ключевалась `(view_id, element_id)`,
и элемент мог быть нарисован на представлении ровно один раз. ADR-0012 §1 принял это как осознанное
ограничение. Владелец продукта решение отменил: разделяемый компонент, нарисованный один раз,
стягивает к себе все линии через всю диаграмму; нарисованный рядом с каждым из потребителей — нет.
Обменный формат ArchiMate разрешает несколько `node` с одним `elementRef`, и любой инструмент,
пишущий его, этим пользуется.

## Решение

**Бокс — это размещение**: одно рисование элемента на одном представлении, с собственной
идентичностью (`view_layout_node.id`). Элемент может иметь сколько угодно размещений.

Граница слоёв не сдвигается ни на миллиметр:

- **Членство остаётся по элементу и версионируется** (`view_element`): «есть ли элемент на
  представлении» — вопрос, который записывают коммиты и читает «где используется» (ADR-0009).
- **Сколько раз он нарисован — layout**: не версионируется, уходит по Save, как координаты
  (ADR-0003). «Draw again» не порождает коммита; удаление одного из двух боксов — тоже. Команда
  `remove-from-view` уходит на сервер только когда представление покидает *последний* бокс.
- **Вложенность — между размещениями** (`parent_node_id`): копия может лежать в контейнере, пока
  оригинал стоит рядом. То же рассуждение, что в ADR-0011, на уровень ниже.
- **Линия имеет концы-размещения** (`view_layout_link.source_node_id` / `target_node_id`,
  null = «где элемент и нарисован»). Перетащить конец можно **только** на бокс того же элемента —
  диаграмма выбирает, *где* нарисована линия, но никогда — *что* она утверждает
  (`validateConnection` в канвасе).

В редакторе всё, что адресует бокс, адресует размещение: выделение, вложенность, порядок
наложения, изломы, удаление с представления. Всё, что говорит о смысле, — элемент: команды,
свойства, «где используется», буфер обмена, Magic Connector.

## Аудит схемы (2026-08-22)

Проведён против живой базы после V14, с требованием «элемент может повторяться, и связи между
дублями могут различаться» в руках.

### A1. Одна линия на связь на представление — не закрыто, требует V15

`view_layout_link` ключуется `(view_id, link_key)`: у связи на представлении **ровно одна линия**.

Что уже работает: у каждой связи свои концы, поэтому *разные* связи распределяются по разным
дублям — линия R1 идёт к копии B1, линия R2 к копии B2. Это и есть большая часть требования.

Что не работает: **одну связь нельзя нарисовать двумя линиями** — к B1 *и* к B2 одновременно.
Обменный формат это разрешает (несколько `connection` с одним `relationshipRef`), Archi так
рисует, и импорт такого файла сейчас молча схлопнул бы линии до одной. Без V15 импортёр OEF
(следующий пункт плана) начнёт с потери данных.

### A2. Дыры целостности: ссылка может указать в чужое представление

Ничто в базе не требует, чтобы `parent_node_id`, `source_node_id` и `target_node_id` указывали на
размещение **того же представления** — FK ведут в `view_layout_node(id)` без учёта `view_id`.
Сейчас это соблюдает клиент; философия проекта — «база — последний рубеж против плохого импорта»
(регексп слага продублирован check-ограничением ровно поэтому), и с импортёром на подходе дыра
перестаёт быть теоретической.

Третья дыра того же рода: база не проверяет, что `source_node_id` — размещение именно исходного
элемента связи. Для явных связей это выводимо из `relationship_version`, для выводимых линий
(`relationship_id is null`) — невыводимо в принципе. Проверяется приложением; закрыть в БД можно
только денормализацией элемента в строку линии — решить при V15, не раньше.

### A3. Скрытие остаётся по связи — правильно, но решение зафиксировать

`view_hidden_relationship` прячет связь целиком. С одной линией на связь это одно и то же; после
V15 «скрыть связь» (все её линии) и «убрать одну из её линий» (удалить строку этой линии)
разойдутся — и обе операции останутся выразимы без изменения этой таблицы.

### A4–A5. Верно как есть

Членство по элементу (A4) — намеренно, см. решение. `on delete set null` на концах линии (A5):
удаление бокса возвращает линию к первому боксу элемента — потеря на гонке стоит движения мыши,
не информации (ADR-0003).

## План V15 — линия получает собственную идентичность (≈1 день)

Симметрично V14: то, что сделали с боксом, делаем с линией.

1. **Схема.** `view_layout_link.id uuid` PK (как `view_layout_node.id` в V14); `(view_id,
   link_key)` перестаёт быть уникальным — это «что линия утверждает», а не «какая это линия».
   Попутно закрыть A2: `unique (view_id, id)` на `view_layout_node`, составные FK
   `(view_id, parent_node_id)` и `(view_id, source_node_id)` / `(view_id, target_node_id)` →
   `view_layout_node (view_id, id)`.
2. **Сервер.** `LayoutLink` получает `id`; save удаляет отсутствующие строки (как узлы в V14).
3. **Клиент.** `vertices` и `linkEnds` ключуются id линии; `canvasLinks` строит линию на каждую
   сохранённую строку плюс одну по умолчанию для связи без строк; у линии в контекстном меню
   появляется «Draw again» — вторая линия той же связи к другой паре боксов.
4. **Проверки.** Блок в драйвере: два бокса, конец линии перетащен на копию, вторая линия той же
   связи, Save, перезагрузка, обе линии на местах.
5. **ADR-0012.** Импорт/экспорт `connection` становится взаимно однозначным — это и есть выигрыш.

До V15 ничего из сделанного переделывать не придётся: id линии добавляется поверх, как id бокса
добавился поверх V12–V13.
