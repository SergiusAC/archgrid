# ADR-0003. Трёхслойное разделение: модель / представление / layout

- **Статус:** accepted
- **Дата:** 2026-08-17

## Контекст

Исходная идея предполагала раздельное хранение семантической модели и визуального layout. Практика показывает, что двух слоёв недостаточно: состав представления (какие элементы на нём показаны) — семантическое решение, а координаты — нет.

## Решение

Три слоя с разными свойствами:

| Слой | Содержание | Версионирование | Конфликты |
|---|---|---|---|
| Semantic model | Элементы, связи, типы, свойства | Коммитами | Транзакция + валидация |
| View definition | Viewpoint, состав элементов и связей, фильтры | Коммитами | Транзакция |
| Layout | Координаты, размеры, waypoints, стили | Нет; мутабельно, optimistic lock | Last-write-wins |

## Обоснование

- **Чистая история.** Перетаскивание прямоугольников не попадает в лог изменений. В диффе видно «добавлена связь Payment → Kafka», а не сорок изменений координат. Без этого история модели бесполезна.
- **Авто-layout как обычная операция.** Layout можно пересчитать целиком, не порождая семантического изменения.
- **Открывает путь к CRDT только для layout** (см. ADR-0005), где конфликты безобидны, не подвергая риску корректность модели.

## Следствие: инвариант I1

Элемент существует независимо от того, изображён ли он хоть на одной диаграмме. Отсюда обязательное требование к UI: операции «убрать с представления» и «удалить из модели» различаются явно, вторая показывает остальные использования элемента и требует подтверждения.

Это главное отличие от инструментов рисования и типичное место, где подобные продукты теряют доверие пользователя.

## Последствия

- Три набора API и три канала синхронизации вместо одного.
- Клиент держит два независимых стора (`modelStore`, `layoutStore`), синхронизируемых отдельно.
- Экспорт представления требует соединения всех трёх слоёв.
