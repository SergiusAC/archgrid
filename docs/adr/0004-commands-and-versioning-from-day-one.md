# ADR-0004. Изменения модели — только команды; версии в схеме с первого дня

- **Статус:** accepted
- **Дата:** 2026-08-17

## Контекст

Формула продукта включает «Git» — диффы моделей, привязку архитектурных решений к изменениям, состояние на дату, review изменений. При этом сама функциональность истории по плану появляется только в фазе 5.

## Решение

1. **Единственный путь мутации модели — команда.** Прямых UPDATE из контроллеров нет. Конвейер: authz → optimistic check по `baseCommitId` → apply к in-memory снимку → validate по метамодели → транзакционный commit → инвалидация индексов → broadcast.
2. **`commit_id` присутствует в версионируемых таблицах начиная с фазы 2**, независимо от того, что UI истории появится только в фазе 5.
3. Текущее состояние материализуется в `element_current` / `relationship_current` и обновляется в той же транзакции.

## Обоснование

- Ретрофит версионирования в невидоизменённую схему требует переписывания каждого запроса и каждого репозитория. Стоимость закладки сейчас — дни; стоимость ретрофита позже — недели.
- Команды дают бесплатно: undo/redo на клиенте, аудит, идемпотентный импорт, безопасный интерфейс для AI (см. ADR-0006).
- Валидация в одной точке гарантирует инвариант I2: модель не может прийти в состояние, недопустимое метамоделью, каким бы путём изменение ни пришло.

## Требование к сообщениям валидации

Отказ должен объяснять, а не только запрещать: «Serving недопустима между Application Component и Technology Node; допустимые связи: Assignment, Association». Пользователь учится нотации через инструмент — это существенная часть ценности продукта.

## Последствия

- Больше кода на команду, чем при прямом CRUD.
- Материализованное состояние надо поддерживать в согласии с версиями — покрывается тестами инвариантов.
- Ветвление модели (branch/merge) в v1 не реализуется, но схема с `parent_id` у коммита к нему готова.
