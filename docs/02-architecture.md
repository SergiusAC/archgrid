# ArchGrid — целевая архитектура

## 1. Продуктовый принцип

> Архитектурный граф — source of truth. Диаграммы — его представления. Документация — его проекция. AI — его читатель и соавтор.

Из этого следует три инварианта, которым подчинена вся система:

- **I1.** Элемент модели существует независимо от того, изображён ли он хоть на одной диаграмме.
- **I2.** Ни одна операция не может привести модель в состояние, недопустимое метамоделью. Валидация — на сервере, в домене, а не в UI.
- **I3.** Любое семантическое изменение модели атрибутировано: кто, когда, зачем. Перемещение прямоугольника семантическим изменением не является.

**Почему модульный монолит.** Один разработчик, on-prem-поставка, домен с сильной связностью (валидация связей требует всей метамодели и всего графа). Микросервисы здесь оплачивались бы распределёнными транзакциями и умножением стоимости внедрения. Границы модулей при этом проводятся строго — через package-private API и тесты архитектурных правил (ArchUnit), — чтобы выделение сервиса позже было механическим, если понадобится.

## 3. Три раздельных хранилища смысла

Это ключевое решение, из которого растёт всё остальное.

| Слой | Что хранит | Версионируется | Конфликты |
|---|---|---|---|
| **Semantic model** | Элементы, связи, типы, свойства | Да, коммитами | Разрешаются транзакцией + валидацией |
| **View definition** | Какие элементы и связи входят в представление, viewpoint, фильтры | Да, коммитами | Как модель |
| **Layout** | Координаты, размеры, waypoints, стили | Нет (мутабельно, optimistic lock) | Безобидны, last-write-wins |

Разделение view definition и layout — неочевидное, но важное. Оно даёт:

- **Чистый лог изменений.** Перетаскивание прямоугольников не засоряет историю. В диффе видно «добавлена связь Payment → Kafka», а не 40 изменений координат.
- **Возможность CRDT позже** только для layout, без риска для корректности модели (см. `01-tech-stack-review.md` §4).
- **Авто-layout как first-class операцию:** layout можно полностью пересчитать, не трогая смысл.

## 4. Модель данных

### 4.1. Метамодель (справочные данные, загружаются из спецификации)

```
metamodel_element_type(code PK, layer, aspect, name, description, notation_shape)
metamodel_relationship_type(code PK, name, category, strength_order)
metamodel_permitted(source_type FK, target_type FK, relationship_type FK, derived bool)
metamodel_viewpoint(code PK, name, description)
metamodel_viewpoint_type(viewpoint FK, element_type FK)   -- палитра
```

Наполняется из версионированного файла `metamodel/archimate-3.2.yaml`, транскрибированного из спецификации. Загрузка при старте с проверкой контрольной суммы; расхождение файла и БД — фатальная ошибка запуска, а не тихая миграция.

### 4.2. Модель (версионируется)

```
model(id PK, workspace_id, key, name, head_commit_id)

commit(id PK, model_id, parent_id, author_id, created_at, message, adr_id NULL)

element(id PK, model_id, key UNIQUE(model_id,key))
element_version(element_id FK, commit_id FK, type FK, name, documentation,
                properties JSONB, parent_element_id NULL, deleted bool,
                PRIMARY KEY(element_id, commit_id))

relationship(id PK, model_id, key UNIQUE(model_id,key))
relationship_version(relationship_id FK, commit_id FK, type FK,
                     source_element_id, target_element_id, name,
                     properties JSONB, deleted bool,
                     PRIMARY KEY(relationship_id, commit_id))
```

`key` — стабильный человекочитаемый идентификатор (`payment-service`), нужен для round-trip в DSL и Git. `id` — UUID, стабилен навсегда и не меняется при переименовании.

**Материализация текущего состояния.** Запрос «состояние на HEAD» через версии дорог. Держим денормализованные `element_current` / `relationship_current`, обновляемые в той же транзакции, что и коммит. Историю читаем только когда её явно спрашивают.

### 4.3. Представления и layout

```
view(id PK, model_id, key, name, viewpoint FK, kind)          -- versioned
view_version(view_id, commit_id, name, viewpoint, deleted)
view_member(view_id, commit_id, element_id NULL, relationship_id NULL)  -- состав: versioned

view_layout(view_id PK, version bigint)                       -- mutable, optimistic lock
view_layout_node(view_id FK, element_id FK, x, y, w, h,
                 parent_node_id NULL, style JSONB)
view_layout_edge(view_id FK, relationship_id FK, waypoints JSONB, style JSONB)
```

### 4.4. Поиск, происхождение, аудит

```
element_search(element_id PK, tsv tsvector, embedding vector(1024) NULL)

provenance(fact_id, fact_kind, source_kind, source_ref, imported_at, confidence)
           -- фаза 6: откуда взялся факт (ручной ввод / K8s / OpenAPI / AI)

audit_log(id, workspace_id, actor_id, action, target_kind, target_id, at, payload JSONB)
```

`provenance` появляется в фазе 6, но колонку `source_kind` в `element_version` стоит завести раньше — ретрофит происхождения в готовую модель болезненный.

### 4.5. Мультитенантность

```
workspace(id PK, name, settings JSONB)
```

On-prem обычно = один тенант, но workspace-скоуп закладываем с первого дня: он же служит границей прав доступа, а разделение «прод / песочница / архив» заказчики просят почти сразу. Изоляция — `workspace_id` в каждой таблице + обязательный фильтр на уровне репозитория, проверяемый тестом.

## 5. Поток изменения модели

Единственный путь мутации — команда. Прямых UPDATE из контроллеров нет.

```
Client → POST /api/models/{id}/commands
         { baseCommitId, commands: [ {type: "AddRelationship", ...}, ... ], message }

  1. Authz          — есть ли право менять модель
  2. Optimistic     — baseCommitId == head? иначе 409 + дифф расхождения
  3. Apply          — команды применяются к in-memory снимку графа
  4. Validate       — метамодель: допустима ли связь source→target данного типа;
                      инварианты: нет циклов в composition, нет висячих связей
  5. Commit         — транзакция: новый commit + *_version + обновление *_current
  6. Invalidate     — сброс граф-индекса и поисковых записей затронутых элементов
  7. Broadcast      — WS-уведомление подписчикам представления

→ 200 { commitId, appliedCommands, warnings[] }
→ 422 { violations[] }  — с указанием, какое правило метамодели нарушено
```

Валидация обязана **объяснять**, а не только запрещать: «Serving недопустима между Application Component и Technology Node; допустимые связи: Assignment, Association». Для целевого пользователя это половина ценности продукта — он учится нотации через инструмент.

Команды — тот же формат, в котором AI-sidecar возвращает предложения (фаза 7). Значит AI получает валидацию бесплатно и не может испортить модель.

## 6. Представления: одна модель — много нотаций

Каждое представление — это `(viewpoint, набор элементов, набор связей, layout)`.

- **C4 Context / Container / Component** реализуются как viewpoint'ы поверх ArchiMate-ядра с сопоставлением типов (C4 Container ≈ Application Component / Technology Node в зависимости от природы). Сопоставление задаётся декларативно в том же файле метамодели.
- **Deployment View** — фильтр по Technology-слою + связи Assignment.
- **Security View** — фильтр по тегам/свойствам + слой.
- **UML Sequence** — не проекция графа, а *отдельный вид*: у графа нет порядка вызовов. Требует собственной сущности «сценарий» (упорядоченный список взаимодействий, ссылающихся на существующие связи). Не в MVP; учитывать при проектировании, чтобы не обещать невыполнимого.

**Derived relationships** — сильная сторона ArchiMate и хороший дифференциатор: показать на Context-уровне связь между системами, выведенную из связей их компонентов. Реализуется на in-memory графе по правилу «сила выведенной связи = слабейшая в цепочке». Порядок силы транскрибировать из спецификации, не по памяти.

## 7. Границы модулей (правила, проверяемые ArchUnit)

- `domain` не зависит ни от чего, кроме JDK. Ни Spring, ни JPA, ни Jackson.
- `metamodel` не зависит от `model`; `model` зависит от `metamodel`.
- `ai` зависит только от портов, никогда от репозиториев напрямую.
- Ни один модуль не обращается к таблицам другого модуля — только через его публичный сервис.
- `import` формирует команды и отдаёт их в `model`; собственной записи в БД не ведёт.

## 8. On-prem: требования, влияющие на архитектуру

| Требование | Архитектурное следствие |
|---|---|
| Air-gapped установка | Ни одного обращения в интернет при старте и работе. Все зависимости в образе. Offline-бандл образов (`docker save`). |
| IdP заказчика | OIDC + SAML 2.0 через Spring Security. Своего хранилища паролей нет вообще. |
| Апгрейд силами заказчика | Только forward-миграции Flyway, обратная совместимость API на одну мажорную версию, health/readiness пробы. |
| Бэкап силами DBA | Единственный stateful-компонент — Postgres. `pg_dump` должен быть достаточным для полного восстановления. Файлы (вложения) — в БД либо в S3-совместимом хранилище заказчика. |
| Аудит и комплаенс | `audit_log` на каждое изменение модели и прав, неизменяемый, экспортируемый. |
| Политика отключения AI | Продукт полностью функционален без AI-сайдкара. Флаг на уровне workspace. |
| Лицензирование продукта | Offline-активация по ключу, проверка на уровне workspace. Проектировать как отдельный модуль, не размазывать по коду. |

## 9. Что осознанно отложено

| Отложено | До какой фазы | Почему |
|---|---|---|
| Совместное редактирование в реальном времени | 9 | Presence закрывает большую часть ощущения; co-editing над валидируемой моделью — сложная задача |
| Ветвление модели (branch/merge) | после 9 | Линейной истории хватает надолго; схема к ветвям готова |
| UML Sequence | после 6 | Требует отдельной сущности сценария |
| Кастомная метамодель на тенанта | не планируется в v1 | Взаимоисключающе с гарантией корректности ArchiMate |
| Микросервисная декомпозиция | не планируется | Границы модулей позволяют вернуться к вопросу без переписывания |
