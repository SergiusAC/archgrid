## Фаза 0 — Фундамент ✅ выполнено

**Цель:** пустой, но полностью рабочий скелет, который собирается и деплоится одной командой.

- [x] Монорепо: `server/` (Gradle 9.7, Java 21, **Spring Boot 4.1**), `web/` (Vite 8, React 19, TS 6), `metamodel/`, `deploy/`, `docs/`.
- [x] Структура модулей сервера + правила ArchUnit (`domain` без внешних зависимостей и т.д.) — написаны *до* кода, иначе границы размоются за месяц.
- [x] Postgres (pgvector/pg18) в Docker Compose, Flyway, первая миграция (`workspace`, `model`).
- [x] Аутентификация: OIDC resource server через Spring Security, Keycloak 26.7 в compose с импортом realm.
- [x] CI: сборка, тесты, линт, Testcontainers.
- [x] Health/readiness пробы, structured logging (профиль `prod`), Micrometer/Prometheus.

**Проверено:** `docker compose up` поднимает систему; токен от Keycloak принимается, анонимный вызов даёт 401; `/api/workspaces` возвращает данные из БД; невалидный slug даёт RFC 9457 problem document; 10 тестов зелёные (домен, ArchUnit, интеграционные на Testcontainers).

### Что выяснилось по ходу (актуально для последующих фаз)

- Spring Boot 4.x вынес автоконфигурации в отдельные модули: `org.flywaydb:flyway-core` даёт библиотеку, но миграции запускает только `spring-boot-starter-flyway`. То же с MockMvc — теперь `spring-boot-starter-webmvc-test`, пакет `org.springframework.boot.webmvc.test.autoconfigure`.
- Testcontainers 2.x переименовал все модули в `testcontainers-*` и перенёс классы (`org.testcontainers.postgresql.PostgreSQLContainer`).
- Образы PostgreSQL 18+ требуют монтировать `/var/lib/postgresql`, а не `/var/lib/postgresql/data`.
- Порт БД в dev — **5433**: 5432 на машине разработчика обычно уже занят.

## Фаза 1 — Метамодель как данные (3 недели)

Самая недооцениваемая фаза. Здесь закладывается корректность, ради которой продукт покупают.

- Формат `metamodel/archimate-3.2.yaml`: типы элементов (слой, аспект, форма нотации), типы связей, порядок силы, матрица разрешённых связей, viewpoint'ы и палитры.
- **Транскрипция матрицы из спецификации ArchiMate 3.2, Приложение B.** Не по памяти, не из LLM, не из чужого репозитория без сверки. Заложить 4–5 дней только на это и на перекрёстную проверку.
- Валидатор файла: полнота матрицы, отсутствие противоречий, все ссылки разрешаются.
- Загрузчик в БД при старте с контрольной суммой.
- Домен: `Metamodel`, `ElementType`, `RelationshipType`, `PermittedRelationships`, `Validator`.
- Правила деривации связей + тесты на контрольных примерах из спецификации.
- Сопоставление C4 ↔ ArchiMate в том же файле.

**Готово, когда:** `validator.check(sourceType, targetType, relType)` даёт корректный ответ с объяснением на всей матрице, тесты по примерам из спецификации проходят.

**Риск:** ошибка в матрице обнаруживается только у пользователя и стоит доверия. Митигация: авто-проверка симметрий и явный ручной обзор по слоям.

## Фаза 2 — Ядро модели и API (3 недели)

- Схема БД: `element`, `element_version`, `relationship`, `relationship_version`, `commit`, `*_current`.
- Доменные команды: `CreateElement`, `RenameElement`, `SetProperty`, `AddRelationship`, `DeleteRelationship`, `DeleteElement`, `MoveElement` (вложенность).
- Обработчик команд: authz → optimistic check → apply → validate → commit → invalidate.
- Порт `GraphRepository` + Postgres-адаптер (рекурсивные CTE) + in-memory граф-индекс с инвалидацией по версии.
- REST + OpenAPI: модель, элементы, связи, команды.
- Ответ 422 с человекочитаемым объяснением нарушенного правила.

**Готово, когда:** через API можно построить `Payment Service → Kafka → Notification Service`, недопустимая связь отвергается с объяснением, история коммитов пишется.

## Фаза 3 — Редактор (5 недель)

Самая большая фаза по объёму UI-работы.

- Канвас на React Flow: узлы по типам ArchiMate с корректной нотацией, вложенность, связи с маркерами по типу.
- Палитра, ограниченная viewpoint'ом текущего представления.
- Drag-to-connect с **живой подсказкой допустимости**: при протягивании связи подсвечиваются валидные цели, недопустимые гасятся. Это и есть «система понимает, что это архитектурные объекты» из идеи.
- Разделение сторов: `modelStore` (семантика) и `layoutStore` (координаты). Синхронизируются с сервером независимо.
- Undo/redo на стеке команд, а не на снимках состояния.
- Model Explorer: дерево по слоям, поиск, «где используется».
- **Явное различение «убрать с представления» и «удалить из модели»** с показом остальных использований. Инвариант I1 из архитектуры.
- Панель свойств: имя, документация, кастомные свойства, теги.
- Экспорт PNG / SVG.

**Готово, когда:** архитектор рисует связку из идеи без документации, видит подсказки допустимости, случайно не удаляет элемент из модели.

## Фаза 4 — Представления и авто-layout (3 недели) → **M1**

- CRUD представлений, выбор viewpoint.
- «Добавить существующий элемент на представление» — из explorer'а и поиском.
- Проекции: C4 Context, C4 Container, Technology/Deployment, ArchiMate Layered.
- Derived relationships с визуальным отличием от явных.
- Авто-layout через `elkjs` (layered + ортогональные рёбра), применение к выделенному фрагменту или ко всему представлению.
- Фильтры представления: по слою, тегу, свойству.

**M1 — демонстрируемый MVP.** Один граф, показанный как C4 Context и как Deployment View. Это уже можно показывать людям и получать обратную связь.

## Фаза 5 — Версионирование, DSL, документация (5 недель) → **M2**

- История модели: список коммитов, дифф двух коммитов (добавлено / удалено / изменено), просмотр состояния на момент.
- ADR: сущность решения, привязка к коммиту и к затронутым элементам, статусы (proposed / accepted / superseded).
- **DSL / Architecture-as-Code:** текстовое представление модели, двусторонняя конвертация модель ↔ текст, стабильные `key` для читаемых диффов в Git. Экспорт/импорт файла, позже — CLI-валидация в CI.
- Генерация документации arc42 из модели: шаблон, подстановка описаний и диаграмм, экспорт Markdown / HTML / PDF.
- Postgres FTS: полнотекстовый поиск по элементам и документации.

**M2 — можно отдавать design partners.** Есть история, обоснования решений и документация — то, за что платят корпоративные архитекторы. Здесь имеет смысл остановить разработку и 2–3 недели поговорить с реальными архитекторами, прежде чем идти в фазу 6.

## Фаза 6 — Импорт и reconciliation (7 недель) → **M3**

Самая тяжёлая инженерная фаза. Она же — главный ответ на вопрос «чем вы лучше draw.io».

**6a. Импорт из инструментов (2 недели)**
- ArchiMate Open Exchange File Format (XML) — импорт и экспорт. Открывает миграцию из Archi, BiZZdesign, Sparx.
- Structurizr DSL — импорт.
- PlantUML C4 — импорт (best-effort).
- draw.io — импорт геометрии с ручной типизацией (честно предупреждать, что это полуавтоматика).

**6b. Импорт из артефактов (2 недели)**
- OpenAPI 3.x → Application Service, Application Interface, зависимости между сервисами.
- Kubernetes (манифесты и/или live-кластер через kubeconfig) → Node, Technology Service, Deployment.
- Terraform (state / plan JSON) → инфраструктурные узлы.

**6c. Reconciliation (3 недели) — здесь настоящая сложность**
- Модель происхождения: у каждого факта источник, время, уверенность.
- Правила сопоставления сущностей: один сервис приходит из трёх источников под тремя именами.
- Разрешение расхождений: что делать, если K8s говорит одно, а архитектор нарисовал другое. Ручной ввод по умолчанию побеждает, расхождение помечается как drift.
- **Architecture drift report** — «модель разошлась с реальностью вот здесь». Это самостоятельная продаваемая фича, и ради неё стоит вся фаза.
- Повторный импорт идемпотентен и не создаёт дубликатов.

**M3.** С этого момента граф не устаревает сам собой — снят главный риск продукта.

## Фаза 7 — AI Copilot (5 недель) → **M4**

Первый Python-код проекта. Всё за портом `LlmProvider`, продукт работает при выключенном AI.

- Python sidecar на FastAPI: stateless, без БД, узкий контракт.
- Абстракция провайдера: OpenAI-совместимый endpoint (покрывает Azure OpenAI, vLLM, Ollama) + Claude API. Конфигурируется заказчиком.
- **Text → Model:** описание системы текстом → набор команд изменения модели. Возвращает команды, а не граф, — валидацию и права обеспечивает Java. Ошибочные предложения физически не могут испортить модель.
- **AI architecture review:** анализ фрагмента модели на типовые проблемы (циклические зависимости, точки отказа, нарушения слоёв, неописанные элементы).
- **Semantic search:** эмбеддинги элементов и документации в `pgvector`, поиск смыслом. Локальная embedding-модель в сайдкаре, чтобы работало в air-gap.
- **Подсказки при рисовании:** предложение следующего элемента/связи по контексту.
- Генерация черновиков ADR и разделов arc42.
- Impact analysis: обход графа делает Java, формулирует последствия человеческим языком — LLM.

Все AI-результаты — **предложения с явным подтверждением**. Никакой автоматической записи в модель.

## Фаза 8 — Enterprise readiness (6 недель) → **M5**

Фаза, без которой on-prem не продаётся, и которую соло-разработчики систематически недооценивают.

- RBAC: роли на workspace и модель (viewer / contributor / owner / admin), проверка на уровне репозитория.
- SAML 2.0 в дополнение к OIDC (крупные заказчики чаще на SAML).
- Аудит: неизменяемый лог, UI просмотра, экспорт.
- Helm chart, ресурсные лимиты, пробы, конфигурация через ConfigMap/Secret.
- Offline-бандл образов, установка в air-gap, документированная процедура апгрейда и отката.
- Лицензирование: offline-ключ, ограничения по числу пользователей/моделей.
- Резервное копирование и восстановление: документированная процедура, проверенная на практике.
- Руководства: администратора, пользователя, интеграций.
- Базовая безопасность: зависимости без известных уязвимостей, security headers, rate limiting, готовность к внешнему пентесту (заказчики его потребуют).

**M5 — продаваемая on-prem v1.**

## Фаза 9 — Совместное редактирование (5 недель)

- Presence (курсоры, выделение соавторов) — стоит вынести раньше, в фазу 4: дёшево и сильно улучшает ощущение продукта.
- CRDT **только для layout** (координаты, waypoints), через отдельный документ на представление.
- Семантическая модель остаётся транзакционной: команды, валидация, коммиты.
- UI разрешения конфликта версий: показать дифф, предложить rebase команд.

## Порядок, который я бы не менял

1. **Метамодель до редактора.** Иначе редактор придётся переписывать, когда выяснится, что типы устроены иначе.
2. **Версионирование в схеме до фичи версионирования.** `commit_id` в таблицах с фазы 2, UI истории — в фазе 5.
3. **Импорт после документации, а не до.** Импортировать в модель, которую нельзя версионировать и документировать, бессмысленно.
4. **AI после импорта.** AI над пустой моделью — демонстрация; AI над импортированным реальным ландшафтом — продукт.
5. **Enterprise readiness перед первой продажей, а не после.** Отсутствие SAML или процедуры бэкапа убивает сделку на этапе техаудита независимо от качества продукта.

## Главные риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Ошибки в матрице ArchiMate | Высокая | Критическое (потеря доверия) | Транскрипция из спецификации, авто-проверки, ручной обзор по слоям, тесты по контрольным примерам |
| Reconciliation окажется вдвое дороже оценки | Высокая | Сдвиг сроков на 1–2 месяца | Начать с одного источника (K8s), довести до конца, потом расширять |
| Цикл enterprise-продажи 6–12 месяцев для соло-основателя | Высокая | Проект не дойдёт до выручки | Искать 2–3 design partners уже на M2, не ждать M5 |
| Объём UI-работы в фазе 3 | Средняя | Сдвиг на 2–3 недели | Резать функциональность редактора, не качество валидации |
| Требования комплаенса (SOC 2, пентест) на первой сделке | Средняя | Блокирует сделку | Выяснять требования на этапе пилота, а не при подписании |
| Выгорание от 9-месячного цикла в одиночку | Средняя | Критическое | M1 через 4 месяца как психологическая контрольная точка; показывать работу людям, не ждать «готовности» |

## Ближайшие шаги

1. Утвердить или оспорить решения в `01-tech-stack-review.md` — прежде всего отказ от Neo4j.
2. Завести Git-репозиторий (сейчас каталог не под контролем версий).
3. Начать фазу 0: скелет монорепо, Docker Compose, CI.
4. Параллельно с фазой 0 — начать транскрипцию матрицы ArchiMate: это работа руками, её можно вести кусками между задачами.
