## Сверка с фактическим состоянием (2026-08-17)

План писался до кода, и часть его разошлась с реальностью. Ниже — где именно, без подгонки задним числом.

### Фазы 4 и 3 перемешались

Представления, членство элементов в них, авто-layout и **сохранение layout** планировались на фазу 4, а сделаны в фазе 3: без представления канвасу нечего рисовать, а без сохранения позиций редактор бесполезен после перезагрузки. Из фазы 4 остались проекции C4/Deployment, деривация связей и фильтры.

Практически: **веха M1 достигнута примерно на неделю раньше** заявленного, но объём фазы 3 оказался больше запланированного ровно на эту разницу. Суммарная оценка не изменилась.

### Фаза 1 закрыта, кроме одного пункта

Метамодель, C4-сопоставление и профили сделаны. Открытым остаётся **порядок силы структурных связей** — единственное значение, которого нет в данных Archi. Он нужен только движку деривации, то есть фазе 4, и до неё не блокирует ничего.

### Что появилось сверх плана

- **Профили** (ArchiMate Specialization of Concepts) — плана не было, добавлены после вопроса про Specialization. Оказались санкционированным языком способом расширения и уточнили ADR-0002.
- **Workspace как репозиторий с одним графом** ([ADR-0008](adr/0008-one-graph-per-workspace.md)) — исправление дефекта проектирования, найденного при просмотре UI.
- **Папки** для элементов и представлений ([ADR-0009](adr/0009-views-and-folders.md)) — не планировались вовсе.
- **Драйвер UI-проверки** как project-skill — не планировался; появился после того, как три визуальных дефекта прошли мимо всех тестов.

### Что оказалось недооценено

**Проверка UI.** В плане её не было как отдельной работы. По факту это единственный способ находить целый класс дефектов: пять из них — двойная обёртка маркеров, пустая мини-карта, меню за краем экрана, наложение узлов, `fitView` до layout — не ловятся ни `tsc`, ни линтом, ни 67 серверными тестами. Долг зафиксирован ниже отдельным разделом.

**Пересмотры структуры от взгляда на UI.** Две правки предметной области (ADR-0008 и ADR-0009) пришли не из кода, а из «посмотрел на экран и не сходится». Это не потери — это самый дешёвый момент их находить, — но в плане такого этапа не было.

### Оценка вперёд менялась один раз

Фаза 4 сократилась примерно на треть за счёт сделанного авансом. Фаза 6 выросла на неделю
(2026-08-20): обменный формат ArchiMate — полторы недели работы, а не строка в списке из четырёх
импортёров ([ADR-0012](adr/0012-archimate-exchange-format.md)). Остальные фазы как были.

## Фаза 0 — Фундамент ✅ выполнено

- [x] Структура модулей сервера + правила ArchUnit (`domain` без внешних зависимостей и т.д.) — написаны *до* кода, иначе границы размоются за месяц.
- [x] Postgres (pgvector/pg18) в Docker Compose, Flyway, первая миграция (`workspace`, `model`).
- [x] Аутентификация: OIDC resource server через Spring Security, Keycloak 26.7 в compose с импортом realm.
- [x] CI: сборка, тесты, линт, Testcontainers.
- [x] Health/readiness пробы, structured logging (профиль `prod`), Micrometer/Prometheus.

**Проверено:** `docker compose up` поднимает систему; токен от Keycloak принимается, анонимный вызов даёт 401; `/api/workspaces` возвращает данные из БД; невалидный slug даёт RFC 9457 problem document; 10 тестов зелёные (домен, ArchUnit, интеграционные на Testcontainers).

### Что выяснилось по ходу (актуально для последующих фаз)

- Spring Boot 4.x вынес автоконфигурации в отдельные модули: `org.flywaydb:flyway-core` даёт библиотеку, но миграции запускает только `spring-boot-starter-flyway`. То же с MockMvc — теперь `spring-boot-starter-webmvc-test`, пакет `org.springframework.boot.webmvc.test.autoconfigure`.
- Testcontainers 2.x переименовал все модули в `testcontainers-*` и перенёс классы (`org.testcontainers.postgresql.PostgreSQLContainer`).
- Образы PostgreSQL 18+ требуют монтировать `/var/lib/postgresql`, а не `/var/lib/postgresql/data`.
- Порт БД в dev — **5433**: 5432 на машине разработчика обычно уже занят.

**Решение по источнику (2026-08-17):** транскрипция из спецификации заменена на использование данных Archi (MIT, коммит зафиксирован, файлы вендорены в `metamodel/upstream/archi/`), связи приняты как валидные. Сверка с XSD The Open Group выполнена: словарь совпадает точно, матрица и палитры приняты по авторитету Archi. Протокол — `metamodel/VERIFICATION.md`.

- [x] Домен: `Metamodel`, `ElementType`, `RelationshipType`, `Layer`, `Aspect`, `RelationshipCategory`, `Viewpoint`, `RelationshipVerdict`.
- [x] Загрузчик YAML с строгими проверками.
- [ ] Порядок силы структурных связей — единственное значение не из upstream, помечено как непроверенное. Требует Приложения B.
- [ ] Движок деривации связей (правило слабейшего звена) — типы готовы, обход графа в фазе 4.
- [x] Сопоставление C4 ↔ ArchiMate — `metamodel/c4-mapping.yaml`, написан руками отдельно от генерируемого файла, валидируется против метамодели при загрузке. Решения в [ADR-0007](adr/0007-c4-projection.md): C4 не хранится, а вычисляется как глубина относительно фокуса; направление связи в C4 и ArchiMate противоположно.
- [x] Профили (ArchiMate Specialization of Concepts): домен `Profile`, `AttributeDefinition`, `ProfileCatalog` с разрешением имени типа в базовый концепт, миграция `V2__profile.sql`. Уточнение к [ADR-0002](adr/0002-metamodel-as-data.md): это санкционированный языком способ расширения, дающий заказчику «Microservice» без отказа от соответствия.
- [ ] Проекция метамодели в БД — отложена до фазы 2, когда появятся таблицы `element`/`relationship`, на которые она будет ссылаться. Тогда же `element_version` получит `profile_id`.

**Готово:** `metamodel.check(source, target, relationship)` работает на всей матрице и объясняет отказ («Serving is not permitted from Application Component to Data Object. Permitted instead: Access, Association.»). 55 тестов зелёные.

**Риск остаётся:** матрица не сверена с первоисточником. Смягчение: словарь сверен, целостность и плотность проверяются тестами, три пустые ячейки зафиксированы явно.

## Фаза 2 — Ядро модели и API ✅ выполнено

- [x] Схема БД (`V3__model_graph.sql`): `model_commit`, `element`, `element_version`, `relationship`, `relationship_version`. **Диапазоны валидности вместо `*_current`** — обоснование в `docs/02-architecture.md` §4.2.
- [x] Доменные команды: `CreateElement`, `RenameElement`, `SetElementDocumentation`, `SetElementProperty`, `DeleteElement`, `AddRelationship`, `DeleteRelationship`. Ссылаются на объекты по slug, а не по UUID — это делает лог команд читаемым, диффы DSL осмысленными, а предложения AI выполнимыми.
- [x] Конвейер: authz → optimistic check по `baseCommitId` → применение к снимку в памяти → валидация по метамодели → транзакционный коммит.
- [x] REST: создание модели, применение команд, чтение элементов, связей и истории.
- [x] Ответ 422 с перечнем всех нарушений и объяснением каждого; 409 с обоими id коммитов при расхождении версий.

**Проверено сквозным тестом:** через API строится `Payment Service → Kafka → Notification Service`; `Serving` из Application Component в Data Object отвергается с объяснением и списком допустимых альтернатив; отвергнутый батч не меняет ничего; история пишется с автором и сообщением; профиль модели используется как тип элемента. 43 теста зелёные.

### Найдено и исправлено по ходу

Catch-all `@ExceptionHandler(Exception.class)`, написанный в фазе 0, перехватывал `AccessDeniedException` до фильтра Spring Security и `ResponseStatusException` до резолвера статусов. Следствие: **любой отказ в доступе возвращался как 500 «Internal error»**, и 404 тоже. Дефект относится к безопасности и был бы замечанием на техаудите. Исправлено явным пробросом; закреплено тестами на 403 и 404.

### Отложено осознанно

- Порт `GraphRepository` и in-memory граф-индекс для обхода: `ModelGraph` уже загружается целиком в память, отдельный индекс нужен только под impact analysis (фаза 4).
- Связи, нацеленные на другие связи (ArchiMate это допускает): вторая пара nullable-колонок эндпойнтов, когда появится сценарий.
- Проекция метамодели в БД: остаётся ненужной, метамодель загружается из файла при старте.

Самая большая фаза по объёму UI-работы.

- [x] `GET .../models/{m}/profiles` — специализации модели для палитры.
- [x] Канвас на React Flow с типизированными узлами, цвета слоёв ArchiMate, стереотипы `«Microservice»`.
- [x] Палитра, ограниченная viewpoint'ом; профили отдельной группой над базовыми концептами.

- [x] Undo/redo на стеке команд: undo применяет обратные команды и порождает новый коммит, а не переписывает историю.

### Второй инкремент — по итогам просмотра редактора живьём

Раньше связи рисовались без направления вовсе.
- [x] **Мини-карта** — не работала, потому что у узлов не было явных `width`/`height`.

### Тестирование фронтенда — долг закрыт

Долг закрыт 2026-08-20. До этого у `web/` были только `tsc -b` и `oxlint`, ни одного тестового
файла: сервер покрыт тестами, клиент — нулём, и три дефекта, дошедшие до пользователя, были прямым
следствием.

- [x] **Vitest + юнит-тесты на чистую логику клиента.** 42 теста на `Metamodel`
      (`permits`/`permittedBetween`/`explain`/`palette` — разбор буквенной матрицы), `invert()`,
      `notationFor`, `slugify`/`uniqueKey`. Гоняются на каждый push вместе с линтом и сборкой.

      **Написание тестов сразу нашло три дефекта, ни один из которых не ловился ничем другим:**
      `uniqueKey` спрашивал `in` вместо `Object.hasOwn` — элемент с именем «Constructor» получал
      ключ `constructor-2` на пустой модели; `invert` разворачивал плоский список целиком, из-за
      чего отмена удаления присылала связи **раньше** элемента, и сервер отвергал весь батч как
      висячий конец; и она же не возвращала элемент **на представление** — он появлялся в
      репозитории, а канвас не менялся, что читается как «undo не сработал».
- [x] **Драйвер `run-archgrid` в CI отдельным job'ом.** `browser` в `.github/workflows/ci.yml`:
      поднимает Postgres и Keycloak через compose, собирает `bootJar`, ждёт `/actuator/health`,
      засевает workspace, отдаёт собранный бандл через `vite preview` и гоняет оба режима
      (`smoke` 18, `interactions` 84). Скриншоты выкладываются артефактом всегда — включая
      `failure.png` при падении. Запускается на pull request и на push в main, но не на каждый
      push в ветку: прогон занимает минуты.

      Проверено локально ровно тем же путём — против собранного бандла, а не dev-сервера. Заодно
      выяснилось, что `server.proxy` в конфиге Vite работает только в разработке: у `preview` свой
      блок, и без него весь job упал бы на первом запросе к API при полностью здоровом приложении.

Компонентные тесты (React Testing Library) сознательно не планируются: для одного разработчика они дают меньше всего на единицу поддержки, ломаются от рефакторинга разметки, а их классы дефектов частично закрыты двумя пунктами выше.

### Третий инкремент — Explorer и панель свойств

- [x] **Панель свойств**: переименование, документация, произвольные свойства и **атрибуты профиля отдельными полями по объявленному типу** (`string`/`number`/`boolean`/`date`/`time`/`currency`). Правки фиксируются по потере фокуса, а не по нажатию клавиши: каждое изменение — коммит, а история по символу на запись нечитаема. До этого переименовать элемент в UI было нельзя вообще — созданный «Application Component» так и оставался с именем типа.
- [x] **Model Explorer**: все элементы модели, а не только нарисованные, сгруппированные по слоям, с поиском по имени, ключу и типу, числом связей и действием «add to view» для тех, кого нет на представлении. Именно здесь центральное утверждение продукта становится видимым: модель — это вещь, а диаграмма — один её вид.
- [x] «Где используется» в панели свойств и в контекстном меню, с переходом к связанному элементу.
- [x] Драйвер расширен до 15 проверок, включая **отсутствие перекрытий узлов**.

**Найдено при просмотре:** новые элементы клались поверх существующих — позиция вычислялась по счётчику элементов, а не по занятости холста. Узел, спрятанный за другим, выглядит как несозданный, то есть хуже, чем неаккуратная диаграмма.

### Четвёртый инкремент — workspace как репозиторий

Замечание при просмотре UI: слово «модель» значило две разные вещи, а элементы нельзя было переиспользовать между моделями. Второе оказалось не неудобством, а дефектом ценности продукта — обход графа, ограниченный одной моделью из трёх, отвечал бы на «где используется» неполно и молча. Решение в [ADR-0008](adr/0008-one-graph-per-workspace.md).

- [x] Миграция `V4`: `unique (workspace_id)` на `model`, граф каждому workspace, отказ с объяснением при нескольких моделях вместо молчаливого слияния.
- [x] Из API убран сегмент `/models/{key}`: `/api/workspaces/{ws}/elements`, `/commands`, `/commits`, `/profiles`.
- [x] Граф создаётся лениво при первом обращении, идемпотентной вставкой `on conflict do nothing`.
- [x] Из UI убран выбор и создание модели; единственный workspace открывается сразу; вкладка называется «Repository».

**Найдено при проверке:** первая загрузка страницы шлёт три запроса разом, каждый пытался создать граф, и проигравший гонку получал нарушение constraint — а в PostgreSQL это аборчивает транзакцию целиком, поэтому перехват исключения с повторным чтением работать не мог в принципе.

### Пятый инкремент — представления, папки, workspace

`docs/05-ui.md` — описание интерфейса и критический разбор с пятнадцатью проблемами. Три первых меняют ощущение от продукта сильнее остального вместе взятого:

1. **Ctrl+Z не отменяет перемещение прямоугольника.** Архитектурно верно (координаты не идут через команды), для пользователя — неожиданно: он двигает бокс, жмёт Ctrl+Z и получает отмену переименования пятиминутной давности. Нужны два независимых стека.
2. **Тип связи выбирается до протягивания.** Метамодель уже умеет отвечать, что допустимо между двумя элементами; сейчас это знание используется только чтобы запрещать. Показывать меню допустимых типов на отпускании — превращает главную фичу из запрещающей в подсказывающую.
3. **Созданный элемент получает имя своего типа** и требует перехода в правую панель. Нужно редактирование по месту сразу после создания.

### Найдено и исправлено

Маппинг ролей выдавал `ROLE_owner`, а `hasAnyRole('OWNER')` требует `ROLE_OWNER` — Spring сравнивает строки с учётом регистра. Все мутации возвращали 403 при настоящем токене Keycloak. Тесты этого не ловили, потому что подставляли authorities напрямую и ни разу не прогоняли код, читающий реальный токен. Конвертер теперь нормализует регистр (заказчик может назвать роль как угодно), и на него написаны отдельные тесты.

- Канвас на React Flow: узлы по типам ArchiMate с корректной нотацией, вложенность, связи с маркерами по типу.
- Палитра, ограниченная viewpoint'ом текущего представления.
- Drag-to-connect с **живой подсказкой допустимости**: при протягивании связи подсвечиваются валидные цели, недопустимые гасятся. Это и есть «система понимает, что это архитектурные объекты» из идеи.
- Разделение сторов: `modelStore` (семантика) и `layoutStore` (координаты). Синхронизируются с сервером независимо.
- Undo/redo на стеке команд, а не на снимках состояния.
- Model Explorer: дерево по слоям, поиск, «где используется».
- **Явное различение «убрать с представления» и «удалить из модели»** с показом остальных использований. Инвариант I1 из архитектуры.
- Панель свойств: имя, документация, кастомные свойства, теги.
- Экспорт PNG / SVG.

**Готово, когда:** архитектор рисует связку из идеи без документации, видит подсказки допустимости, случайно не удаляет элемент из модели.

## Фаза 4 — Представления, деривация, проекции ✅ закрыта

Сокращена примерно на треть: представления, членство, авто-layout и сохранение layout сделаны авансом в фазе 3.

владельца продукта, второй переведён в долг проверки и ничего не блокирует.**

1. **C4 — отложен.** Deployment не делаем, и **сама проекция C4 под вопросом**: владелец продукта

   таблица сопоставления, `C4Projection` и пункт меню остаются как есть.
2. **Порядок силы структурных связей** не сверен с Приложением B и переезжает в общий долг проверки
   метамодели рядом с матрицей ([VERIFICATION.md](../metamodel/VERIFICATION.md)). После
   [ADR-0013](adr/0013-no-derived-connections-on-views.md) от него не зависит ничего, что видит
   пользователь: деривация осталась внутри проекции C4 и будущего анализа влияния. Ни одну фазу он
   не блокирует — блокирует только заявления о соответствии и точность анализа влияния, когда тот
   появится.

**M1 изменился по содержанию, а не по срокам.** Формулировка «один граф как C4 Context и как
Deployment View» больше не является целью: Deployment отложен, C4 пересматривается. И сам C4 Context
после ADR-0013 показывает боксы без линий, если связи между системами не проведены в модели явно —
линии между их внутренностями представление больше не поднимает. Демонстрировать M1 имеет смысл на
редакторе, представлениях и фильтрах, а не на проекции.

### Сделано

- [x] **Движок деривации связей** (`RelationshipDerivation`). Два правила по цепочке, все промежуточные элементы которой скрыты: цепочка структурных связей выводит слабейшую; цепочка структурных, завершающаяся одной зависимостью или динамической связью, выводит её. За зависимость деривация не продолжается — цепочка, вышедшая из структуры, больше не описывает то же самое.

- [x] Выводимые связи **вычисляются, никогда не хранятся**, и приходят отдельным списком с путём вывода: диаграмма умеет ответить «почему здесь эта линия».

      продукта ([ADR-0013](adr/0013-no-derived-connections-on-views.md)):** представление рисует

      проекция C4 и будущий анализ влияния. Цена решения и инструкция по возврату — в ADR.
- [x] `GET .../elements/{key}/usage` — связи и **представления**, на которых элемент есть.

**Проверялось сквозным сценарием** (до ADR-0013): `Payment System` содержит `Payment API`, тот обслуживает `Notification System`; контекстное представление с двумя системами показывало выводимую Serving с путём через «Payment API». ## Фаза 6 — Импорт и reconciliation (8 недель) → **M3**

Самая тяжёлая инженерная фаза. Она же — главный ответ на вопрос «чем вы лучше draw.io».

**6a. Импорт из инструментов (3 недели)**

Было две недели на четыре импортёра. Один только обменный формат — это полторы недели, и делать
вид, что он помещается в четверть, значит сдвинуть срок втихую вместо того, чтобы сдвинуть его
вслух.

*Решение о грязных файлах — принято и реализовано в домене (2026-08-22).* Файл, нарушающий
метамодель, импортируется **толерантно**: всё допустимое принимается, недопустимое отбрасывается
поимённо, отчёт — часть результата ([ADR-0015](adr/0015-import-tolerance.md)). Механизм —
`ModelChange.applyForImport`: граф после импорта валиден по построению, `POST /commands` остаётся
строгим. Импортёру остаётся разбор файла в команды.

*Подготовка (1.5 дня) — сделано 2026-08-20.* Две дыры, которые импорт нашёл бы, провалившись
в них: команды `set-relationship-property` не существовало (свойства связи хранились и
читались, а записать их было нечем), и **профиль нельзя было создать вообще** — единственная
запись в таблицу во всём репозитории жила в тестовой фикстуре. Теперь есть команда и
`POST` / `DELETE /profiles` с проверкой по тем же правилам, по которым каталог проверяется при
загрузке. Профили при этом **не версионируются**: у таблицы нет интервала валидности, и история
не может сказать, когда изменился словарь. Это названное ограничение, а не позиция.

*ArchiMate Model Exchange File Format — импорт и экспорт (1.5 недели).* Целевой формат обмена,
единственный вендоронезависимый для ArchiMate; открывает миграцию из Archi, BiZZdesign, Sparx.
Решения и цена расхождений — [ADR-0012](adr/0012-archimate-exchange-format.md).

- [ ] Разбор `<elements>`, `<relationships>`, `<organizations>`, `<propertyDefinitions>` в команды —
      импорт идёт через тот же конвейер, что и всё остальное ([ADR-0004](adr/0004-commands-and-versioning-from-day-one.md)),
      а не в обход него в базу.
- [ ] `<views>`: `node` → `view_element` + `view_layout_node`, `Container` → вложенность,
      `connection` → членство, `NestingRelationship` → вложенность плюс скрытая связь,
      отсутствующее соединение → `view_hidden_relationship`.
- [x] ~~Схлопывание дублей узлов~~ — отменено: дубли импортируются как размещения, и с V15 то же
      верно для линий — несколько `connection` одной связи ложатся строками `view_layout_link`
      ([ADR-0014](adr/0014-placements.md)). Узел ↔ размещение, connection ↔ линия: соответствие
      обменному формату взаимно однозначное. D-002 закрыт.
- [ ] **Префикс идентификаторов на экспорте:** `xs:ID` — это NCName и не может начинаться с цифры,
      а наш slug может (ADR-0012, §4). Без этого файл не проходит валидацию по схеме стандарта.
- [ ] Экспорт: обратное преобразование, включая `NestingRelationship` и пропуск скрытых связей.
- [ ] **Тест валидирует экспорт против XSD** и проходит round-trip на моделях из Archi. Формат,
      который мы не проверяем схемой, — это формат, про который мы узнаем от клиента.
- [ ] Отчёт импорта: что схлопнуто, что потеряно (стили), что интерпретировано.

*Остальные инструменты (1.5 недели).*
- Structurizr DSL — импорт.
- PlantUML C4 — импорт (best-effort).
- draw.io — импорт геометрии с ручной типизацией (честно предупреждать, что это полуавтоматика).

**6b. Импорт из артефактов (2 недели)**
- OpenAPI 3.x → Application Service, Application Interface, зависимости между сервисами.
- Kubernetes (манифесты и/или live-кластер через kubeconfig) → Node, Technology Service, Deployment.
- Terraform (state / plan JSON) → инфраструктурные узлы.

**6c. Reconciliation (3 недели) — здесь настоящая сложность**
- Модель происхождения: у каждого факта источник, время, уверенность.
- Правила сопоставления сущностей: один сервис приходит из трёх источников под тремя именами.
- Разрешение расхождений: что делать, если K8s говорит одно, а архитектор нарисовал другое. Ручной ввод по умолчанию побеждает, расхождение помечается как drift.
- **Architecture drift report** — «модель разошлась с реальностью вот здесь». Это самостоятельная продаваемая фича, и ради неё стоит вся фаза.
- Повторный импорт идемпотентен и не создаёт дубликатов.

**M3.** С этого момента граф не устаревает сам собой — снят главный риск продукта.

## Фаза 7 — AI Copilot (5 недель) → **M4**

Первый Python-код проекта. Всё за портом `LlmProvider`, продукт работает при выключенном AI.

- Python sidecar на FastAPI: stateless, без БД, узкий контракт.
- Абстракция провайдера: OpenAI-совместимый endpoint (покрывает Azure OpenAI, vLLM, Ollama) + Claude API. Конфигурируется заказчиком.
- **Text → Model:** описание системы текстом → набор команд изменения модели. Возвращает команды, а не граф, — валидацию и права обеспечивает Java. Ошибочные предложения физически не могут испортить модель.
- **AI architecture review:** анализ фрагмента модели на типовые проблемы (циклические зависимости, точки отказа, нарушения слоёв, неописанные элементы).
- **Semantic search:** эмбеддинги элементов и документации в `pgvector`, поиск смыслом. Локальная embedding-модель в сайдкаре, чтобы работало в air-gap.
- **Подсказки при рисовании:** предложение следующего элемента/связи по контексту.
- Генерация черновиков ADR и разделов arc42.
- Impact analysis: обход графа делает Java, формулирует последствия человеческим языком — LLM.

Все AI-результаты — **предложения с явным подтверждением**. Никакой автоматической записи в модель.

---

## Фаза 8 — Enterprise readiness (6 недель) → **M5**

Фаза, без которой on-prem не продаётся, и которую соло-разработчики систематически недооценивают.

- RBAC: роли на workspace и модель (viewer / contributor / owner / admin), проверка на уровне репозитория.
- SAML 2.0 в дополнение к OIDC (крупные заказчики чаще на SAML).
- Аудит: неизменяемый лог, UI просмотра, экспорт.
- Helm chart, ресурсные лимиты, пробы, конфигурация через ConfigMap/Secret.
- Offline-бандл образов, установка в air-gap, документированная процедура апгрейда и отката.
- Лицензирование: offline-ключ, ограничения по числу пользователей/моделей.
- Резервное копирование и восстановление: документированная процедура, проверенная на практике.
- Руководства: администратора, пользователя, интеграций.
- Базовая безопасность: зависимости без известных уязвимостей, security headers, rate limiting, готовность к внешнему пентесту (заказчики его потребуют).

**M5 — продаваемая on-prem v1.**

## Фаза 9 — Совместное редактирование (5 недель)

- Presence (курсоры, выделение соавторов) — стоит вынести раньше, в фазу 4: дёшево и сильно улучшает ощущение продукта.
- CRDT **только для layout** (координаты, waypoints), через отдельный документ на представление.
- Семантическая модель остаётся транзакционной: команды, валидация, коммиты.
- UI разрешения конфликта версий: показать дифф, предложить rebase команд.

## Порядок, который я бы не менял

1. **Метамодель до редактора.** Иначе редактор придётся переписывать, когда выяснится, что типы устроены иначе.
2. **Версионирование в схеме до фичи версионирования.** `commit_id` в таблицах с фазы 2, UI истории — в фазе 5.
3. **Импорт после документации, а не до.** Импортировать в модель, которую нельзя версионировать и документировать, бессмысленно.
4. **AI после импорта.** AI над пустой моделью — демонстрация; AI над импортированным реальным ландшафтом — продукт.
5. **Enterprise readiness перед первой продажей, а не после.** Отсутствие SAML или процедуры бэкапа убивает сделку на этапе техаудита независимо от качества продукта.

## Главные риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Ошибки в матрице ArchiMate | Высокая | Критическое (потеря доверия) | Транскрипция из спецификации, авто-проверки, ручной обзор по слоям, тесты по контрольным примерам |
| Reconciliation окажется вдвое дороже оценки | Высокая | Сдвиг сроков на 1–2 месяца | Начать с одного источника (K8s), довести до конца, потом расширять |
| Цикл enterprise-продажи 6–12 месяцев для соло-основателя | Высокая | Проект не дойдёт до выручки | Искать 2–3 design partners уже на M2, не ждать M5 |
| Объём UI-работы в фазе 3 | Средняя | Сдвиг на 2–3 недели | Резать функциональность редактора, не качество валидации |
| Требования комплаенса (SOC 2, пентест) на первой сделке | Средняя | Блокирует сделку | Выяснять требования на этапе пилота, а не при подписании |
| Выгорание от 9-месячного цикла в одиночку | Средняя | Критическое | M1 через 4 месяца как психологическая контрольная точка; показывать работу людям, не ждать «готовности» |
